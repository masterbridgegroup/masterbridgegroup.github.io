복습 한 스푼 🥄

어제(Day 49)는 2주차 종합 테스트를 봤어요. 딱 하나만 다시: 이진 탐색은 정렬된 자료에만 쓸 수 있고 O(log₂n), 해싱은 주소를 계산해 O(1)로 찾는다는 점이었죠. 마지막 문제에서 Git이 형상 관리 도구라고 나왔는데, 오늘부터 그 형상 관리를 본격적으로 배웁니다.

1. 형상 관리란? — 소프트웨어의 변경 일지

형상 관리(SCM, Software Configuration Management)는 소프트웨어를 개발하는 동안 생기는 모든 산출물의 변경 사항을 기록하고 통제하는 활동이에요. "형상"(Configuration)은 어렵게 들리지만 관리 대상이 되는 결과물이라는 뜻입니다.

비유 — 여러 사람이 하나의 보고서를 같이 쓴다고 생각해 보세요. 누가 언제 무엇을 고쳤는지 기록해 두지 않으면, 어제 잘 되던 내용이 사라지거나 두 사람이 서로의 수정을 덮어써 버립니다. 형상 관리는 이 수정 일지와 되돌리기(Undo) 기능을 소프트웨어 전체에 적용하는 일이에요.

중요한 점은 소스 코드만 관리 대상이 아니라는 것이에요.

관리 대상(형상 항목)예시
개발 문서요구사항 명세서, 설계서, 시험 계획서
소스 코드프로그램 원본 코드
실행 파일컴파일 결과물, 라이브러리
관련 자료사용자 매뉴얼, 데이터베이스 구조 정의서
시험 포인트 — "형상 관리의 대상은 소스 코드뿐이다"라는 보기는 틀린 문장입니다. 개발 과정에서 나오는 모든 산출물(문서 포함)이 대상이에요. 이 함정이 매우 자주 나옵니다.

2. 베이스라인 — 기준이 되는 저장 시점

베이스라인(Baseline, 기준선)은 개발 과정 중 어느 시점에 정식으로 검토·승인되어 고정된 산출물을 말해요. 이 시점 이후에는 정해진 절차 없이는 함부로 바꿀 수 없습니다.

비유 — 게임에서 세이브 포인트와 같아요. "여기까지는 확실히 맞다"고 도장을 찍어 저장해 두는 지점입니다. 이후 문제가 생기면 이 세이브 포인트로 되돌아갈 수 있고, 여기서부터 무엇이 바뀌었는지도 정확히 알 수 있죠.

보통 개발 단계마다 베이스라인을 설정합니다.

베이스라인확정되는 시점
기능 베이스라인요구사항 분석이 끝나 요구사항 명세서가 승인된 때
설계 베이스라인설계가 끝나 설계서가 승인된 때
제품 베이스라인개발이 끝나 제품(실행 파일)이 승인된 때
시험 포인트 — "개발 과정의 특정 시점에서 변경을 통제하기 위한 기준이 되는 것"의 답은 베이스라인(기준선)입니다. 단어 그대로 물어보는 문제가 자주 출제됩니다.

3. 형상 관리 4대 활동 — 식·통·감·기

형상 관리는 네 가지 활동으로 이루어져요. 순서까지 외워야 합니다.

순서활동하는 일
①형상 식별
(Identification)		관리할 대상에 이름과 번호(식별자)를 붙여 목록을 만듦. 베이스라인의 기준이 됨
②형상 통제
(Control)		변경 요청을 받아 검토·승인하고 반영. 승인 없는 변경을 막음
③형상 감사
(Audit)		변경이 요구사항대로 제대로 반영됐는지 검증
④형상 기록
(Status Accounting, 상태 보고)		변경 과정과 결과를 문서로 기록해 관계자에게 보고
외우는 법 — "식별 → 통제 → 감사 → 기록"을 "식·통·감·기"로 묶어 두세요. 이름을 붙이고(식), 바꿀지 결정하고(통), 제대로 됐나 확인하고(감), 적어 남긴다(기)는 자연스러운 순서예요.
시험 포인트 — 4대 활동 중 순서를 묻는 문제와 "형상 감사"의 뜻을 묻는 문제가 핵심입니다. 형상 감사는 변경이 올바르게 됐는지 확인하는 검증 활동이며, 기록·보고하는 것은 형상 기록입니다. 둘을 바꿔 놓은 보기에 주의하세요.

4. 형상 통제 위원회(CCB)와 변경 처리 흐름

변경 요청이 들어왔을 때 아무나 마음대로 고치면 안 되므로, 형상 통제 위원회(CCB, Configuration Control Board)라는 의사 결정 조직이 승인 여부를 판단해요.

단계내용
1. 변경 요청오류 수정·기능 추가 등의 요청서를 제출
2. 영향 평가바꾸면 어디까지 영향이 가는지, 비용·일정은 어떤지 분석
3. 승인 / 기각CCB가 판단해 승인하거나 거절
4. 변경 수행승인된 것만 반영하고 새 버전을 만듦
5. 검증 및 기록제대로 됐는지 확인(감사)하고 이력을 남김(기록)
비유 — 아파트에서 벽을 허물려면 관리사무소의 허가가 필요하죠. CCB가 그 관리사무소 역할이고, "이 벽 허물면 윗집 바닥이 무너질까?"를 따지는 게 영향 평가예요.
시험 포인트 — 변경 관리에서 가장 중요한 단계는 영향 평가(영향 분석)입니다. 또 승인되지 않은 변경은 반영하지 않는다는 원칙이 자주 출제됩니다.

5. 형상 관리를 하면 무엇이 좋을까

이점설명
변경 이력 추적누가·언제·왜 고쳤는지 알 수 있어 문제 원인을 빨리 찾음
이전 버전 복구잘못 고쳤을 때 예전 상태로 되돌리기 가능
동시 작업 가능여러 개발자가 같은 프로젝트를 덮어쓰기 걱정 없이 작업
중복·누락 방지같은 일을 두 번 하거나 빠뜨리는 실수를 줄임
가시성 확보프로젝트 진행 상황을 수치와 기록으로 확인
내일 예고 — Day 51에서는 이 형상 관리를 실제로 해 주는 버전 관리 도구(공유 폴더 방식 · 클라이언트/서버 방식 · 분산 저장소 방식)를 배웁니다.
시험 포인트 — 형상 관리의 목적을 묻는 문제에서 "프로그램의 실행 속도를 높인다" 같은 성능 관련 보기는 항상 오답입니다. 형상 관리는 변경의 추적·통제가 목적이에요.
